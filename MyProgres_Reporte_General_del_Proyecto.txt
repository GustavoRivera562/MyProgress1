1. Resumen ejecutivo
MyProgres es una aplicación móvil Android orientada al seguimiento del entrenamiento de fuerza, el progreso personal y la hidratación. Busca que el usuario registre sus ejercicios y series de forma rápida, consulte su evolución, gestione descansos y mantenga un control diario del consumo de agua. La experiencia combinará una interfaz deportiva de aspecto premium con almacenamiento local y sincronización en la nube.
La aplicación se diseñará con enfoque offline-first: las operaciones principales deberán funcionar sin conexión y guardarse primero en el dispositivo mediante Room. Cuando exista conectividad, un proceso de sincronización enviará los cambios pendientes a Firebase. La seguridad se incorporará desde el diseño mediante autenticación, autorización por usuario, validación de datos, protección de credenciales, reglas de Firebase y pruebas específicas.
2. Objetivos del producto
Registrar entrenamientos, ejercicios, pesos y repeticiones por serie.
Administrar los tiempos de descanso con temporizador y aviso al finalizar.
Registrar el consumo de agua y visualizar el avance respecto de una meta diaria.
Mostrar historial y evolución del rendimiento a lo largo del tiempo.
Incorporar un avatar animal personalizable que evolucione por constancia, fuerza y objetivos.
Permitir el uso sin Internet y sincronizar los datos al recuperar conectividad.
Proteger la cuenta y los datos personales, evitando accesos entre usuarios.
Detectar, registrar y comunicar errores de manera clara y segura.
3. Usuarios y alcance funcional
El usuario principal es una persona que entrena fuerza y quiere llevar un registro sencillo, consistente y visual de su actividad. La aplicación no reemplaza asesoría médica, nutricional ni profesional del entrenamiento. Los objetivos de hidratación y las métricas serán orientativos y deberán explicarse como tales.

6. Funcionamiento offline y online
La estrategia propuesta es offline-first y Room-first: Room será la fuente principal de verdad para la experiencia en el dispositivo; Firestore actuará como destino remoto de sincronización. Firestore también ofrece persistencia offline en Android, pero mantener una política local explícita permite controlar mejor las operaciones, estados, reintentos y conflictos.
El usuario registra una serie, consumo de agua o sesión.
La aplicación valida los datos y los guarda primero en Room.
Si la escritura local termina correctamente, la interfaz confirma el registro.
La operación queda marcada como pendiente de sincronización si todavía no se ha confirmado en la nube.
WorkManager detecta que hay conectividad y procesa la cola de operaciones pendientes.
La aplicación envía cada operación con un identificador único e idempotente.
Al recibir confirmación remota, actualiza el estado local a sincronizado.
Si falla la conexión, conserva el dato local y programa un nuevo intento.
7. Seguridad de la información
La seguridad se aplicará en capas. La validación visual mejora la experiencia, pero no sustituye la validación del repositorio ni las reglas de autorización del servidor.
7.1 Identidad, autenticación y sesiones
Usar Firebase Authentication para gestionar identidad y autenticación.
Asociar los datos de cada cuenta al UID autenticado.
No almacenar contraseñas ni tokens manualmente en Room, archivos de texto o registros.
Implementar recuperación de cuenta y cierre de sesión.
Al cerrar sesión, impedir que la siguiente cuenta acceda a datos privados de la sesión anterior; definir limpieza o aislamiento de cachés locales.
Considerar reautenticación para operaciones especialmente sensibles, si el alcance lo requiere.
7.2 Autorización y aislamiento de datos
Cada registro remoto debe pertenecer a un usuario autenticado.
Las reglas de Firestore deben comparar el UID autenticado con el propietario del documento.
El cliente no debe poder asignar libremente el propietario de un registro.
Probar lectura, creación, modificación y eliminación con usuarios distintos.
Aplicar el mismo aislamiento en las consultas locales y al cambiar de cuenta.
7.3 Ejemplo conceptual de regla
match /users/{userId}/{document=**} {
  allow read, write: if request.auth != null
                     && request.auth.uid == userId;
}
Este fragmento es ilustrativo y no debe copiarse como política final sin adaptarlo a la estructura real de Firestore. Las reglas definitivas también deben validar campos, tipos, tamaños y operaciones permitidas.

7.5 Dispositivo, almacenamiento y comunicaciones
Utilizar HTTPS/TLS para comunicaciones remotas.
No incluir claves privadas ni secretos de servidor dentro de la aplicación.
Usar Android Keystore para proteger material criptográfico local cuando sea necesario.
Guardar preferencias sensibles mediante mecanismos de almacenamiento adecuados.
Solicitar únicamente permisos Android necesarios para las funciones reales.
Mantener dependencias y SDK actualizados y revisar vulnerabilidades conocidas.
Evitar mostrar tokens, rutas internas, stack traces o detalles de base de datos en mensajes visibles.
7.6 App Check y límites de protección
Firebase App Check complementa Authentication y Security Rules: ayuda a reducir solicitudes desde clientes no autorizados, pero no demuestra que el usuario tenga permiso para acceder a un dato. La autorización sigue dependiendo de reglas correctamente diseñadas. Ninguna de estas medidas garantiza invulnerabilidad; se requiere pruebas, monitoreo y mantenimiento.
7.7 Privacidad
Recolectar únicamente los datos necesarios para prestar las funciones.
No incluir nombre, correo, peso, altura, tokens ni otra información sensible en Analytics o Crashlytics.
Documentar qué datos se recopilan, con qué finalidad, dónde se almacenan y cuánto tiempo se conservan.
Definir un flujo de cierre de cuenta y eliminación de datos asociados.
Evitar información sensible en notificaciones visibles en la pantalla bloqueada.
Preparar política de privacidad y revisar requisitos legales aplicables antes de publicar.
8. Gestión y reporte de errores
Se implementará un manejo centralizado para clasificar errores, informar al usuario y conservar información técnica mínima para diagnóstico. Los errores no deben provocar pérdida silenciosa de datos.

8.2 Canales de comunicación
Interfaz: Snackbar, diálogo o texto junto al campo, con lenguaje claro y acción sugerida.
Registro local: tabla ErrorLog en Room para eventos que requieren seguimiento.
Monitoreo remoto: Crashlytics para cierres, ANR y excepciones no fatales seleccionadas.
Centro de diagnóstico: vista técnica para desarrollo o soporte, sin exponer detalles al usuario final.
8.3 Registro local ErrorLog
No guardar contraseñas, tokens, correos, nombres, peso, altura, contenido privado ni trazas completas en ErrorLog. Crashlytics gestionará la información de diagnóstico de excepciones, también con minimización de datos. El propio registrador debe tener un mecanismo de fallback para evitar ciclos si falla al intentar registrar un error.

15. Cierre
MyProgres se plantea como una aplicación de entrenamiento centrada en el usuario, con una experiencia visual clara, registro confiable y capacidad de operar sin conexión. La prioridad técnica es construir una base sólida: persistencia local, aislamiento de datos, validación en capas, sincronización segura y gestión centralizada de errores. Las funciones visuales y motivacionales se integrarán sobre esa base, con pruebas verificables antes de cada etapa de publicación.
